# Design Document

## Feature: astro-site-scaffold

### Stage 1 — Averon Overseas Website Scaffold

---

## Overview

This document describes the technical design for Stage 1 of the Averon Overseas website: a fully-configured Astro project scaffold that establishes every structural foundation the site needs before any page content is written.

Stage 1 produces a buildable, deployable Astro 5 project with:

- A deterministic `astro.config.mjs` driven by a single `SITE_URL` environment variable
- Design-token CSS (`src/styles/tokens.css`) with light/dark mode and reduced-motion support
- Self-hosted WOFF2 fonts (Young Serif, Hanken Grotesk, JetBrains Mono) copied from `@fontsource` packages
- A `Base.astro` layout wrapping every page with `<head>` metadata, skip link, Header, `<main>`, and Footer
- A `Header.astro` component with sticky nav, language selector, and mobile `<details>` menu
- A `Footer.astro` component with company details on the night-background token
- An i18n string skeleton (`src/i18n/`) with a `useTranslations()` utility
- A typed JSON data schema for categories and products with `import.meta.glob` helpers
- A `formatSpec()` notation helper with eight unit tests
- `@astrojs/sitemap` integration and a dynamically-generated `robots.txt` Astro endpoint
- A GitHub Actions workflow for automatic GitHub Pages deployment

No page content (home, product listings, etc.) is created in this stage. All work in Stage 1 is purely structural and will be consumed by Stage 2 onward.

---

## Architecture

The project is a **zero-client-JS static Astro site** deployed to GitHub Pages. The build pipeline is entirely server-side: Astro SSG renders every `.astro` page at build time, emitting static HTML, CSS, and asset files into `dist/`.

```
┌─────────────────────────────────────────────────────┐
│  GitHub push to main                                │
│           │                                         │
│           ▼                                         │
│  .github/workflows/deploy.yml                       │
│      └─ withastro/action  (npm run build)           │
│           │                                         │
│           ▼                                         │
│       dist/  (static HTML/CSS/assets)               │
│           │                                         │
│           ▼                                         │
│  actions/deploy-pages → GitHub Pages                │
└─────────────────────────────────────────────────────┘
```

### Key architectural decisions

| Decision | Rationale |
|---|---|
| Single `SITE_URL` env var | All absolute URLs (sitemap, canonical, robots.txt) derive from one value. Switching from GitHub Pages to a custom domain requires changing only this variable. |
| Astro endpoint for `robots.txt` | A static `public/robots.txt` cannot reference the runtime `SITE_URL`. An `.ts` endpoint runs at build time and writes the file with the correct value. |
| `@fontsource` packages + copy step | Fonts are installed as npm packages (auditable, version-pinned), then WOFF2 files are copied to `public/fonts/` during setup so they are served as static assets with correct cache headers. |
| `<details>` mobile nav | Zero JS. The native `<details>/<summary>` open/close behavior works without any JavaScript bundle. A small `<script>` inline listener closes the menu when a link is activated (≤200 bytes, inlined). |
| `import.meta.glob` for data | Astro's built-in glob import handles HMR and type-safe JSON loading without a custom file-read abstraction. |
| `useTranslations` fallback chain | Component → locale JSON → `en.json` → raw key string. This prevents empty labels appearing on screen even before translations are reviewed. |

### `astro.config.mjs`

```js
import { defineConfig } from 'astro/config';
import sitemap from '@astrojs/sitemap';

const SITE_URL = process.env.SITE_URL ?? 'https://averonoverseas.github.io';

export default defineConfig({
  site: SITE_URL,
  base: '/',
  output: 'static',
  integrations: [sitemap()],

```

`SITE_URL` is consumed here only. Every other file that needs the canonical origin imports it via `import.meta.env.SITE` (which Astro populates from `site` in the config).

### `src/styles/tokens.css`

Defines all CSS custom properties. No class names or component styles belong here — only tokens.

**Token groups:**

| Group | Properties |
|---|---|
| Colour (light) | `--paper`, `--panel`, `--ink`, `--accent`, `--muted`, `--rule`, `--night`, `--on-night` |
| Colour (dark overrides) | `--paper`, `--panel`, `--ink`, `--muted`, `--rule`, `--night` (accent and on-night unchanged) |
| Typography | `--serif`, `--sans`, `--mono` |
| Color scheme hint | `color-scheme: light / dark` |
| Motion | `prefers-reduced-motion` block |

**Dark mode cascade:**

```
:root { /* light values */ }

@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { /* dark overrides */ }
}

[data-theme="dark"] { /* dark overrides */ }
[data-theme="light"] { /* re-apply light values — beats media query */ }
```

This ensures:
- No `data-theme` + dark OS → dark
- `data-theme="dark"` regardless of OS → dark
- `data-theme="light"` regardless of OS → light
- No `data-theme` + light OS → light (`:root` defaults)

**`@font-face` rules** (six total, one per weight variant):

```css
@font-face {
  font-family: 'Young Serif';
  font-weight: 400;
  font-style: normal;
  font-display: swap;
  src: url('/fonts/young-serif-latin-400-normal.woff2') format('woff2');
}
/* … five more rules for Hanken Grotesk 400/500/700, JetBrains Mono 400/500 */
```

### `src/layouts/Base.astro`

**Props interface:**

```ts
interface Props {
  title: string;           // required, ≤60 chars
  description: string;     // required
  canonicalURL: string;    // required, full absolute URL
  ogImage?: string;        // optional
  lang?: string;           // default 'en'
  dir?: string;            // default 'ltr', overridden for RTL scripts
  alternates?: Array<{ lang: string; url: string }>; // hreflang links
}
```

**RTL auto-detection:** If `lang`'s BCP 47 base subtag is `ar`, `he`, `fa`, or `ur`, `dir` is forced to `"rtl"` regardless of the prop value.

**`<head>` emission order:**
1. `<meta charset="utf-8">`
2. `<meta name="viewport" …>`
3. `<link rel="stylesheet">` → `tokens.css` (first stylesheet)
4. `<title>`
5. `<meta name="description">`
6. `<link rel="canonical">`
7. Open Graph tags (`og:title`, `og:description`, `og:url`, `og:image` when present)
8. `<link rel="alternate" hreflang>` for each entry in `alternates`
9. Organization JSON-LD `<script type="application/ld+json">`
10. Named slot `jsonld` (for per-page JSON-LD injection)

**Body structure:**

```html
<body>
  <a href="#main-content" class="skip-link">Skip to main content</a>
  <Header lang={lang} />
  <main id="main-content">
    <slot />
  </main>
  <Footer lang={lang} />
</body>
```

### `src/components/Header.astro`

**Props:** `lang: string` (default `'en'`)

**Rendering rules:**
- `<header role="banner">` with `position: sticky; top: 0; z-index: 20; background: var(--paper); border-bottom: 1px solid var(--rule)`
- Wordmark block: `<a href="/">` containing `<span>AVERON OVERSEAS</span>` (Young Serif) + `<span>Enable Better Reach</span>` (Hanken Grotesk)
- `<nav aria-label="Main">` with five links; labels from `useTranslations(lang)` — keys: `nav.products`, `nav.specifications`, `nav.howWeSource`, `nav.about`, `nav.contact`
- Language `<select aria-label="…">`: EN (enabled), हिन्दी (disabled), العربية (disabled), Français (disabled), Español (disabled)
- "Request a quote" `<a href="/rfq/">` styled as primary button (filled ink background, accent on hover)
- Mobile breakpoint ≤860 px: hide `<nav>` and desktop CTA; show `<details><summary aria-label="Menu">` containing the same links
- Inline `<script>` (≤200 bytes) closes `<details>` when any child `<a>` is clicked

**No JS bundle.** The inline script is a one-liner event listener attached to the details element, well within the 30 kB JS budget.

### `src/i18n/index.ts`

```ts
type Locale = 'en' | 'hi' | 'ar' | 'fr' | 'es';
type TranslatorFn = (key: string) => string;

export function useTranslations(lang: string): TranslatorFn;
```

**Fallback chain:**
1. Look up `key` in `translations[locale]`
2. If value is empty string or key missing → look up in `translations['en']`
3. If still missing → return the raw `key` string

**Locale validation:** If `lang` is not one of the five supported codes, fall back to `'en'`.

All locale JSON files are imported statically at module load time (no dynamic `import()`), keeping the module synchronous and compatible with Astro's build pipeline.

### `src/utils/formatSpec.ts`

```ts
interface FormatSpecOptions {
  value: string | number;
  unit?: string;
  tol?: string | number;
  isDiameter?: boolean;    // default false
}

export function formatSpec(opts: FormatSpecOptions): string;
```

**Output matrix:**

| `isDiameter` | `unit` present | `tol` present | Output |
|---|---|---|---|
| false | no | no | `"<value>"` |
| false | yes | no | `"<value>\u2009<unit>"` |
| false | yes | yes | `"<value> ± <tol>\u2009<unit>"` |
| false | no | yes | `"<value> ± <tol>"` |
| true | no | no | `"Ø\u2009<value>"` |
| true | yes | no | `"Ø\u2009<value>\u2009<unit>"` |
| true | yes | yes | `"Ø\u2009<value> ± <tol>\u2009<unit>"` |
| true | no | yes | `"Ø\u2009<value> ± <tol>"` |

Rules:
- Numbers passed as `value` are converted via `.toString()` — no rounding, no padding
- `unit` is rendered exactly as provided (callers must pass `"mL"` not `"ml"`)
- U+2009 THIN SPACE is used between value and unit (and after `Ø`)

### `src/pages/robots.txt.ts` — Astro endpoint

An Astro API endpoint that runs at build time and writes the `robots.txt` content. This is the only mechanism that can embed `import.meta.env.SITE` (derived from `astro.config.mjs`) into the file.

```ts
// APIRoute returning plain text
export const GET: APIRoute = ({ site }) => {
  const siteUrl = site?.toString().replace(/\/$/, '') ?? '';
  return new Response(buildRobotsTxt(siteUrl), {
    headers: { 'Content-Type': 'text/plain' },
  });
};
```

The `buildRobotsTxt` function assembles the file per Requirement 11.

## Correctness Properties

*A property is a characteristic or behavior that should hold true across all valid executions of a system — essentially, a formal statement about what the system should do. Properties serve as the bridge between human-readable specifications and machine-verifiable correctness guarantees.*

Most of this feature consists of configuration files, CSS declarations, and static HTML structures where property-based testing is not applicable (IaC-style setup, CSS rule verification, file existence checks). However, several subsystems have genuinely pure, logic-bearing functions with input spaces large enough to benefit from property-based testing:

- **RTL auto-detection** — maps any lang string to a dir value
- **`useTranslations()` fallback chain** — maps (locale, key) pairs through a 3-step fallback
- **Locale validation** — maps any string to a supported locale code or 'en'
- **i18n key parity** — invariant across all non-English locale files
- **Data schema conformance** — invariant across all category and product JSON files
- **`buildRobotsTxt()`** — maps any site URL to a correctly-structured robots.txt string
- **`getCategories()` / `getProducts()`** — data access functions with sort/filter logic
- **Head metadata round-trip** — layout renders all props into the correct `<head>` elements
- **Organization JSON-LD presence** — layout always includes JSON-LD regardless of page props

**Property reflection — redundancy check:**

- Properties 3 (i18n key parity) and 4 (useTranslations fallback) both test i18n correctness but at different levels: 3 tests the JSON files' structural consistency, 4 tests the runtime function's behavior. They are complementary, not redundant.
- Properties 4 (fallback chain) and 5 (invalid locale → en) both test useTranslations. Property 5 is a specific case of Property 4's fallback behavior. However, it tests a distinct code path (locale validation, not key lookup) so it is retained as a separate, focused property.
- Properties 7 (category schema) and 8 (product schema) both test data file conformance. They test different schemas, so both are retained.
- Properties 9 (getCategories sorted) and 10 (getProducts filter) test different behaviors of different functions. Both retained.
- Property 11 (robots.txt structure) subsumes Property 10.4 (Sitemap directive) from the prework. The Sitemap directive check is a subset of the full structural invariant. The properties are merged into one comprehensive robots.txt property.
- Properties 1 (head metadata round-trip) and 2 (Organization JSON-LD) both test Base.astro rendering but for distinct, non-overlapping aspects. Both retained.

After reflection: 10 unique properties remain.

---

### Property 1: Head metadata round-trip

*For any* valid combination of `title`, `description`, `canonicalURL`, optional `ogImage`, and optional `alternates` array passed as props to `Base.astro`, the rendered HTML `<head>` must contain: a `<title>` element whose text equals `title`, a `<meta name="description">` whose `content` equals `description`, a `<link rel="canonical">` whose `href` equals `canonicalURL`, and — when `ogImage` is provided — an `<meta property="og:image">` whose `content` equals `ogImage`; when `ogImage` is absent, no `og:image` meta tag must appear.

**Validates: Requirements 4.3**

---

### Property 2: Organization JSON-LD on every page

*For any* set of page props passed to `Base.astro`, the rendered HTML must include exactly one `<script type="application/ld+json">` element in `<head>` whose parsed JSON contains `@type: "Organization"`, `name: "Averon Overseas"`, a non-empty `email`, a non-empty `telephone` array, and a non-empty `address` object.

**Validates: Requirements 4.11**

---

### Property 3: RTL auto-detection

*For any* `lang` string whose BCP 47 base language subtag is `ar`, `he`, `fa`, or `ur` (e.g. `"ar"`, `"ar-SA"`, `"fa-IR"`), the `<html>` element rendered by `Base.astro` must have `dir="rtl"` regardless of the value of the `dir` prop. *For any* `lang` string whose base subtag is not in that set, the `dir` attribute must equal the `dir` prop value (defaulting to `"ltr"` when absent).

**Validates: Requirements 4.9**

---

### Property 4: `useTranslations` fallback chain

*For any* supported locale `L` and any key `K`, the value returned by `useTranslations(L)(K)` must satisfy: if `translations[L][K]` is a non-empty string then return that value; else if `translations['en'][K]` is a non-empty string then return that value; else return the raw key string `K`. This three-step chain must hold for every possible (locale, key) pair without exception.

**Validates: Requirements 7.4**

---

### Property 5: Invalid locale falls back to English

*For any* string that is not exactly one of `"en"`, `"hi"`, `"ar"`, `"fr"`, `"es"`, calling `useTranslations(invalidLocale)(K)` must return the same value as `useTranslations("en")(K)` for every key `K`.

**Validates: Requirements 7.5**

---

### Property 6: Non-English i18n key parity

*For each* non-English locale file (`hi.json`, `ar.json`, `fr.json`, `es.json`), the set of keys in that file must exactly equal the set of keys in `en.json` — no additional keys, no missing keys — and every value in the non-English file must be an empty string `""`.

**Validates: Requirements 7.3**

---

### Property 7: Category data schema conformance

*For every* JSON file in `src/data/categories/`, the parsed object must conform to the `Category` type: all required fields (`slug`, `name`, `summary`, `order`, `image`, `seoTitle`, `seoDescription`) must be present with their correct types; `summary` length must be ≤160 characters; `seoTitle` length must be ≤60 characters; `seoDescription` length must be ≤155 characters; `image` must end in `.webp` or `.avif`; and `order` values must be unique across all category files.

**Validates: Requirements 8.2**

---

### Property 8: Product data schema conformance

*For every* JSON file in `src/data/products/`, the parsed object must conform to the `Product` type: all required fields must be present with their correct types; `summary` length must be ≤160 characters; `status` must be exactly `"verified"` or `"to-verify"`; `materials`, `variants`, `specs`, `colours`, `standards`, `docs`, `images`, and `tags` must all be arrays; each `specs` entry must have `key`, `value`, and `unit` string fields; each `variants` entry must have `label` (string) and `attrs` (object) fields.

**Validates: Requirements 8.3**

---

### Property 9: `getCategories()` returns ascending-sorted results

*For any* valid set of category JSON files loaded by `getCategories()`, the returned array must be sorted strictly ascending by the `order` field — i.e. for every pair of adjacent elements `a[i]` and `a[i+1]`, `a[i].order < a[i+1].order` must hold.

**Validates: Requirements 8.5**

---

### Property 10: `getProducts()` filter correctness

*For any* valid set of product JSON files and *for any* category slug string `S`:
- `getProducts()` with no argument returns all products
- `getProducts(S)` where `S` matches the `category` field of at least one product returns exactly those products — no products from other categories, and no products with `category === S` omitted
- `getProducts(S)` where `S` matches no product's `category` field returns an empty array `[]`

**Validates: Requirements 8.5**

---

### Property 11: `buildRobotsTxt()` structural invariants

*For any* valid site URL string `U`, `buildRobotsTxt(U)` must return a string that: (a) begins with a `User-agent: *` stanza containing `Allow: /` and no `Disallow` directive with a non-empty value; (b) contains individual stanzas for each of `Googlebot`, `Bingbot`, `GPTBot`, `ClaudeBot`, `Google-Extended`, `PerplexityBot`, and `CCBot`, each with `Allow: /`; (c) contains a `Sitemap:` line whose value is exactly `U` (with trailing slash stripped) followed by `/sitemap-index.xml`; (d) contains no `Disallow:` directive with a non-empty path anywhere in the file.

**Validates: Requirements 10.4, 11.2, 11.3, 11.4, 11.5**

## Error Handling

### Build-time failures

| Scenario | Behaviour |
|---|---|
| `SITE_URL` env var absent | `astro.config.mjs` silently defaults to `'https://averonoverseas.github.io'`; build succeeds. A warning comment in the config documents this default. |
| Malformed category/product JSON | `import.meta.glob` will throw a JSON parse error at build time, failing the build with a clear error message. This is intentional — bad data should fail fast. |
| Missing font WOFF2 file | The CSS `@font-face` src will 404 at runtime but will not break layout; the browser falls back to the declared generic family (Georgia, system-ui, monospace). A setup script step verifies file presence. |
| `getProducts(unknownSlug)` | Returns `[]` — no throw, no warning. Callers must handle empty arrays gracefully. |

### Runtime (static site — no server errors)

Since the site is fully static, there are no runtime server errors. All data is baked at build time. The only runtime error surface is the browser:

| Scenario | Behaviour |
|---|---|
| JS disabled | The site is functional; all navigation is HTML `<a>` elements. The mobile menu (`<details>`) works natively without JS. The inline script for menu-close-on-link is the only JS on the page; its absence is graceful. |
| Fonts fail to load | `font-display: swap` ensures text renders immediately with the fallback stack; fonts swap in when loaded. No layout shift beyond the defined CLS budget. |
| `useTranslations` key miss | Returns the raw key string — visible to developers as a clear "broken translation" signal, not an empty label. |

## Testing Strategy

### Overview

This feature is primarily structural (configuration files, CSS, templates). The testing approach is calibrated to the nature of each subsystem:

| Subsystem | Test type | Rationale |
|---|---|---|
| Project configuration files | Smoke / example | Static verification; no input variation |
| Token CSS values | Example | Fixed expected values; parse-and-compare |
| Font files in `public/fonts/` | Smoke | File existence check |
| Base layout rendering | Property + example | Props vary; head metadata must round-trip |
| RTL detection | Property | Pure function; input space is all lang strings |
| Header/Footer structure | Example | Fixed structural expectations |
| i18n JSON files | Property + example | Key parity across locales; fallback logic |
| `useTranslations()` | Property | Pure function with fallback chain |
| Data schema conformance | Property | Invariant across all JSON files |
| `getCategories()` / `getProducts()` | Property | Sort and filter correctness |
| `formatSpec()` | Example only | Required by Requirement 9.7 explicitly |
| `buildRobotsTxt()` | Property | Pure function; structural invariants |
| GitHub Actions workflow | Smoke | YAML content check |
| Build output | Integration | Full build verification |

### Property-based testing

**Library:** [fast-check](https://github.com/dubzzz/fast-check) (TypeScript-native, zero dependencies, works in Vitest)

Each property test runs a **minimum of 100 iterations**. Tag format in each test:

```ts
// Feature: astro-site-scaffold, Property N: <property text>
```

**Property test implementations:**

**Property 1 — Head metadata round-trip**
Generate arbitrary `{ title, description, canonicalURL, ogImage? }` objects. Render `Base.astro` with these props (via Astro's test utilities or by extracting the head-generation logic to a pure function). Assert all prop values appear correctly in the rendered string.

**Property 2 — Organization JSON-LD on every page**
Generate arbitrary page props. Render layout. Parse the first `<script type="application/ld+json">` in `<head>`. Assert `@type`, `name`, `email`, `telephone`, and `address` are all present with correct values.

**Property 3 — RTL auto-detection**
Generate lang strings from two arbitraries: (a) strings with base subtag in `['ar', 'he', 'fa', 'ur']` with optional region subtag; (b) random strings not in that set. Assert dir is `'rtl'` for group (a) and `'ltr'` (or prop value) for group (b).

**Property 4 — `useTranslations` fallback chain**
Generate (locale, key) pairs. Mock locale JSON with controlled empty/non-empty values. Assert the three-step fallback produces the correct result.

**Property 5 — Invalid locale → en**
Generate arbitrary strings that are not valid locale codes. Assert `useTranslations(invalid)(k)` equals `useTranslations('en')(k)` for all keys.

**Property 6 — Non-English key parity**
Read `en.json` once. For each non-English locale file, verify key set equality and all-empty-string values. (This is a file-system check, not randomized — but modelled as a property across the set of non-English locales.)

**Property 7 — Category schema conformance**
Read all category files. For each file, run schema assertions (required fields, type checks, length limits, unique `order` values). Runs once but across all data files.

**Property 8 — Product schema conformance**
Read all product files. For each file, run schema assertions.

**Property 9 — `getCategories()` sorted**
Use fast-check to generate arbitrary arrays of category objects (with distinct `order` values). Feed them to the sort logic extracted from `getCategories()`. Assert output is strictly ascending by `order`.

**Property 10 — `getProducts()` filter correctness**
Generate arbitrary arrays of product objects with varying `category` values and arbitrary target slugs. Assert filter returns exactly and only the matching products.

**Property 11 — `buildRobotsTxt()` structural invariants**
Generate arbitrary URL strings. Pass to `buildRobotsTxt()`. Parse the output and assert all structural invariants hold.

### Unit tests (example-based)

**`formatSpec.test.ts` — eight required tests** (per Requirement 9.7):

```
(a) plain value with unit          formatSpec({ value: '24.30', unit: 'mm' })       → "24.30\u2009mm"
(b) value with tolerance and unit  formatSpec({ value: '24.30', tol: '0.20', unit: 'mm' }) → "24.30 ± 0.20\u2009mm"
(c) diameter prefix with unit      formatSpec({ value: '34.40', unit: 'mm', isDiameter: true }) → "Ø\u2009 34.40\u2009mm"
(d) mL unit case preservation      formatSpec({ value: '25.70', unit: 'mL' })        → "25.70\u2009mL"
(e) no unit — bare value           formatSpec({ value: '100' })                      → "100"
(f) zero tolerance with unit       formatSpec({ value: '10', tol: '0', unit: 'mm' }) → "10 ± 0\u2009mm"
(g) tolerance without unit         formatSpec({ value: '10', tol: '0.5' })           → "10 ± 0.5"
(h) isDiameter with tol, no unit   formatSpec({ value: '34.40', tol: '0.20', isDiameter: true }) → "Ø\u2009 34.40 ± 0.20"
```
